Solar-Powered Roof Temperature Sensor

A step-by-step build of the independent Wi-Fi temperature node that will sit beside the Pentair solar collectors: firmware first, then breadboard, then perfboard, then into the weatherproof enclosure, then onto the roof.

1How it works

One reading every five minutes, sent over 2.4 GHz Wi-Fi, powered forever by a small panel and a LiPo. The EasyTouch stays the authoritative controller — this node only measures and reports.

The build happens in five phases, each one fully tested before the next begins:

PhaseWhat you doWhat proves it worked
A — FirmwareFlash the bare XIAO at your desk, stand up the MQTT brokerJSON messages arrive on the Pi every 15 s
B — BreadboardWire the sensor, then add the DFR0559 + battery + panel48 h unattended soak on solar/battery power
C — PerfboardMove everything to a soldered “sled” that drops into the boxSame soak test passes on the sled
D — EnclosureDrill glands, mount the sled, seal the boxFull system runs with the lid on, RSSI still healthy
E — RoofTemporary placement, then permanent mountingSeveral days of clean data beside the Pentair sensor

Tools for the day

Soldering iron + solder + flux, wire strippers, small screwdrivers (the DFR0559 and DROK screw terminals are ~2 mm slotted), heat gun or lighter for shrink, drill with a step bit that reaches 12.5–13 mm (a plain 1/2″ bit also works for the gland holes), center punch or awl, painter’s tape, any micro-USB cable (bench-charging the DFR0559), and a USB-C data cable for flashing.

Before roof day Cable ties that live on the roof must be UV-rated (black nylon 6/6 “UV” or stainless). The GTSE saddle-tie pack was dropped from the order — grab UV ties before Phase E, or the panel lead tie-downs will get brittle within a season or two of San Jose sun.

3Read this first — the five rules

Every damaged-board story with this exact parts combination traces back to one of these. Two minutes here saves a reorder.

Rule 1 — verify battery polarity before plugging in JST-PH plug polarity is not standardized between battery brands and board vendors. Meter first: DC volts, red probe to the contact fed by the battery’s red wire — you should read about +3.6 to +4.1 V. Then look at the +/− silkscreen beside the DFR0559’s BAT connectors and confirm the red wire will land on +. If it’s backwards, don’t cut anything — build a crossover from one of your JST-PH pigtail pairs, or use the BAT screw terminal instead (red → +, black → −). The board has a battery-reverse LED; if it ever lights, unplug immediately.
Rule 2 — verify panel VOC before connecting The DFR0559 solar input is rated 4.5–6 V and tolerates ~6.5 V open-circuit, no more. In midday sun, meter the panel’s bare leads with nothing connected: expect ~6.0–6.3 V. At or under 6.5 V → good. Over → don’t connect it (that would be a mislabeled 6 V-class panel). This is also the moment you identify which lead is + for the screw terminal.
Rule 3 — the battery touches only the DFR0559 The XIAO’s own battery pads stay empty forever. Two chargers on one cell fight each other. Power reaches the XIAO exclusively through the USB-A → USB-C cable.
Rule 4 — one USB source at a time on the XIAO When you want to reflash after assembly, unplug the DFR0559’s USB cable from the XIAO first, then connect the computer. Never both at once.
Rule 5 — antenna on before power The ESP32-C3 has no onboard antenna. Snap the U.FL antenna on (press straight down with a fingernail until it clicks) before the board ever transmits, and route it away from the battery and any metal.

A3 · The sketch

Complete firmware. Fill in the four CONFIG lines. TEST_MODE 1 gives 15-second cycles with serial logging; flip to 0 for the production 300-second cycle before roof day.

#include <WiFi.h>
#include <PubSubClient.h>
#include <OneWire.h>
#include <DallasTemperature.h>

// ---------------- CONFIG ----------------
#define TEST_MODE 1                       // 1 = 15 s cycle + serial, 0 = 300 s production
const char* WIFI_SSID  = "YOUR_SSID";     // 2.4 GHz network
const char* WIFI_PASS  = "YOUR_PASSWORD";
const char* MQTT_HOST  = "192.168.1.50";  // Raspberry Pi IP
const char* MQTT_TOPIC = "pool/solar-roof/temperature";
// ----------------------------------------

const uint16_t MQTT_PORT       = 1883;
const char*    SENSOR_ID       = "roof-solar-reference";
const uint32_t SLEEP_SECONDS   = TEST_MODE ? 15 : 300;
const uint32_t WAKE_TIMEOUT_MS = 20000;   // give up and sleep rather than drain the battery

#define ONE_WIRE_PIN D2                   // XIAO C3: GPIO4. (The D2 macro is also correct on a C6.)

RTC_DATA_ATTR uint32_t bootCount = 0;     // survives deep sleep, resets on power loss

OneWire           oneWire(ONE_WIRE_PIN);
DallasTemperature sensors(&oneWire);
WiFiClient        net;
PubSubClient      mqtt(net);

void goToSleep() {
  WiFi.disconnect(true);
  WiFi.mode(WIFI_OFF);
  esp_sleep_enable_timer_wakeup((uint64_t)SLEEP_SECONDS * 1000000ULL);
  esp_deep_sleep_start();                 // never returns
}

void setup() {
  uint32_t t0 = millis();
  bootCount++;

#if TEST_MODE
  Serial.begin(115200);
  delay(2000);                            // USB-CDC needs a moment to enumerate
  Serial.printf("\n[boot %lu] waking\n", (unsigned long)bootCount);
#endif

  // 1 — read the probe before the radio wakes (cleaner power, faster)
  sensors.begin();
  sensors.requestTemperatures();
  float tempF  = sensors.getTempFByIndex(0);
  bool  tempOk = (tempF > -100.0);        // library returns -196.6 F when no probe answers

  // 2 — Wi-Fi, with the hard timeout from the design doc
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) {
    if (millis() - t0 > WAKE_TIMEOUT_MS) goToSleep();
    delay(100);
  }

  // 3 — publish one retained reading
  mqtt.setServer(MQTT_HOST, MQTT_PORT);
  char clientId[32];
  snprintf(clientId, sizeof(clientId), "roofsensor-%06lX",
           (unsigned long)(ESP.getEfuseMac() & 0xFFFFFF));
  while (!mqtt.connect(clientId)) {
    if (millis() - t0 > WAKE_TIMEOUT_MS) goToSleep();
    delay(250);
  }
  char payload[160];
  snprintf(payload, sizeof(payload),
    "{\"sensor\":\"%s\",\"temperature_f\":%.1f,\"temp_ok\":%s,"
    "\"wifi_rssi_dbm\":%d,\"boot_count\":%lu}",
    SENSOR_ID, tempF, tempOk ? "true" : "false",
    WiFi.RSSI(), (unsigned long)bootCount);
  mqtt.publish(MQTT_TOPIC, payload, true);
  mqtt.loop();
  delay(100);                             // let the TCP packet flush before sleeping

#if TEST_MODE
  Serial.printf("[boot %lu] sent: %s\n", (unsigned long)bootCount, payload);
#endif
  goToSleep();
}

void loop() {}                            // never reached — everything happens in setup()
Tip boot_count is stored in RTC memory: it survives deep sleep but resets to 1 on real power loss. Later, on the roof, a counter that unexpectedly restarts from 1 is your brownout detector.

How to read the comparison

WindowExpectIf not…
Stable midday sunThe two roof readings track within a consistent offsetA steady offset is calibration/mounting — note it and move on; it doesn’t block the project
Early-morning warm-upDS18B20 may lead or lag slightly (different thermal mass)Large lag → probe is shaded differently or heat-sunk by its mount
Passing cloudsBrief divergence, re-converging in minutesPersistent divergence → placement problem
Afternoon cool-downSmooth parallel declineErratic jumps on either trace → sensor or connection fault
Health metrics that ride along free boot_count restarting from 1 → the node lost power (battery ran out — check panel shading/charging). Slowly sagging wifi_rssi_dbm → something changed in the RF path. A stuck-but-publishing temperature_f with temp_ok: true → probe reading but thermally decoupled (check its mount).

Feeding this value back into Pentair control logic stays a separate, later project — EasyTouch’s solar input is a physical 10 kΩ thermistor, and this node deliberately doesn’t touch it. (The spare AR-PRO 520272 thermistors from May 2024 are for that future project, not this one.)

7Troubleshooting

SymptomMost likely cause → fix
No serial port after flashing deep-sleep codeThe C3 is asleep when you plug in. Hold B (BOOT), plug USB while holding, release → bootloader mode → upload.
temperature_f: -196.6 / temp_ok: false1-Wire not answering: swapped DATA/VCC at the screw terminal, wire clamped on insulation, or DATA not on D2. Re-check against the printed adapter labels.
Readings appear but are occasionally garbageLoose jumper or cold solder joint on the D2 run — reflow; keep the probe lead away from the USB cable coil.
Wi-Fi never connects2.4 GHz network? Antenna clicked on and taped to the lid? RSSI < −85 at the roof spot → re-aim lid, relocate box within its shade, or see the C6 note in §8.
Publishes but Pi shows nothingBroker bound to localhost (redo A1 step 2), wrong MQTT_HOST IP, or Pi firewall on 1883.
No 5 V at USB OUTON/OFF jumper missing or on OFF — it ships loose in the bag. Then check battery is charged (CHG/DONE LEDs).
CHG LED never lights in sunPanel backwards (reverse LED will say so), VOC test skipped, panel actually shaded, or leads not biting in the screw terminal (tin them).
Battery drains over cloudy stretchesConfirm TEST_MODE 0 (15 s cycles cost 20× the power), check the 20 s timeout is actually firing when Wi-Fi is down (watch a cycle with the router off), verify panel isn’t shaded by afternoon.
boot_count resets from 1 unexpectedlyPower interruption: battery hit cutoff or a connector is intermittent. Check JST seating and battery voltage at the BAT terminal (healthy: 3.5–4.2 V).
Condensation inside the boxSwap in a fresh desiccant packet; confirm glands are tight and on the downward face; consider adding an IP-rated M12 vent plug in a spare drilled hole.

MQTT payload schema

topic: pool/solar-roof/temperature   (retained)

{
  "sensor": "roof-solar-reference",
  "temperature_f": 118.4,
  "temp_ok": true,
  "wifi_rssi_dbm": -67,
  "boot_count": 1532
}

The Pi timestamps on receipt. Battery voltage is deliberately absent — the DFR0559 manages the cell but exposes no state-of-charge signal; adding a fuel gauge is a possible future mod, and boot_count resets already catch the failure case that matters.

If you ever swap in one of your XIAO ESP32-C6 boards

You own three (Aug 18 order) and the sled’s sockets accept them directly. Three differences: (1) the sketch’s D2 macro still lands on the right pin, but it’s GPIO2 there, not GPIO4 — never hardcode the number. (2) The C6 has an onboard ceramic antenna, used by default; nothing to attach. To force the external U.FL instead, enable the RF switch and select it in setup(): set GPIO3 LOW, then GPIO14 HIGH (LOW = built-in). (3) Deep-sleep draw is ~15 µA vs the C3’s ~44 µA — irrelevant next to the DFR0559’s ~1 mA quiescent, so don’t swap for that reason; swap only if the C3 dies or you want the antenna flexibility.
